My interview repositories serve different parts of learning. Some retain solutions. Some help identify a pattern. Others create a place to explain a design, respond to a follow-up, or build a feature under constraints.

An explanation can feel clear while leaving the next problem just as difficult to start. That makes assistance a delicate part of practice: it can help me take the next step, or it can remove the step I needed to learn.

The repositories span years. The older study tools and solution collections predate the December 2025 start of my agentic coding chapter; revisiting and modernizing old work is part of the experience too. They are not all examples of software first generated by an agent.

## From a saved answer to a decision

The LeetCode and [NeetCode submission archives](https://github.com/aranlucas/neetcode-submissions) preserve practice as files that can be revisited. [leetcode-sync](https://github.com/aranlucas/leetcode-sync) includes synchronization and formatting workflows; the private `leetcode` repository keeps problem descriptions, code, and occasional notes together.

An archive answers what I wrote. It does not necessarily help me choose an approach when a new statement appears.

[LeetFlow](https://github.com/aranlucas/leetflow) makes that choice visible through an interactive decision tree. Problem characteristics lead toward a pattern, with a starter template, complexity information, and practice problems nearby. The branches make the reasoning inspectable: why does this problem suggest a sliding window, a heap, or a graph traversal?

The older [leetcode-flashcards](https://github.com/aranlucas/leetcode-flashcards) application offers topic material and a problem browser. Despite its name, the inspected source does not establish a spaced-repetition system. Its useful place in this collection is as another interface around learning material.

[ProblemPrism](https://github.com/aranlucas/leetcode-visualize) brings assistance into the active exercise through a Chrome side panel. It can prepare an explanation for the detected problem and provide hints, visualizations, and requested code review. Reading the current code is a separate review action, giving the learner a distinction between help understanding a question and feedback on an attempt.

These are different ways to address the moment before a solution is complete. The value is in the decision or correction they help the learner make.

## Practice the follow-up

A practical coding exercise often changes after the first answer. A parser gets malformed input. A retry helper needs another error policy. A data structure has to handle a different ordering of events.

My private Java practice repositories make those changes part of the exercise. `samsara-java-screen-practice` contains staged prompts, reference solutions, and tests. `rippling-tech-screen` concentrates on two backend problems: driver payroll and expense rules. The tests make the intended behavior concrete enough to challenge an implementation.

These are preparation materials, not a promise about current employer questions. Their useful feature is that an attempted solution has somewhere to meet a counterexample. A follow-up can reveal whether the design can change without breaking what was already established.

`onsite-lab` expands the practice surface to conversation rounds, technical deep dives, system design, and AI-assisted feature building. It keeps attempts in the browser, supports export, and offers optional feedback against a rubric. A proposed model score remains reviewable rather than becoming the final authority on the attempt.

## Give the discussion a shared object

For system design, the object is a diagram. [System Design Companion](https://github.com/aranlucas/system-design-companion) puts me and the agent on the same Excalidraw canvas. The agent reads components and connections, can see a selection, and can point or make an edit. Saved versions make changes reversible.

In [my account of practicing with it](/blog/practicing-system-design-with-an-ai-on-the-whiteboard), I describe drawing the first pass myself, then asking for hints, capacity estimates, and a rubric review. The agent can respond to the design that is actually on the board, including the part I am pointing at.

That is the clearest connection across the collection. A saved solution, a pattern decision, a test failure, and a shared diagram each give feedback something specific to address. They leave room for me to attempt the work and examine what changes afterward.

Building these tools produces a practice environment. The further test is what happens during practice: whether I can explain a decision, handle the next constraint, or solve a similar problem without the same help. Those are the outcomes worth recording as I keep using it.

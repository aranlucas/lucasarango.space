A GitHub repository can show what was built without explaining the situation that prompted it. As I document my agentic experience, I want each project to have a story about the task, the decisions, and the result.

The goal is to create a home for those accounts and connect them to my professional background and source code.

[lucasarango.space](https://github.com/aranlucas/lucasarango.space) combines an about page, résumé, and Markdown blog. Posts have stable filename-based URLs and a draft flag, so an unfinished account can be reviewed locally before publication.

The résumé comes from a separate structured source. The site also has an assistant whose tools list and read published posts. That lets the writing supply context for questions about my work, with links back to the material behind an answer.

The project list is deliberately smaller than the full GitHub inventory. It provides entry points; the posts can explain the individual experiments in more depth.

The site provides a place to document the work as it develops. Each post follows the problem that prompted a project, the work that went into it, and what happened afterward. That helps distinguish implemented features from outcomes I have actually observed.

The immediate result is a publishing workflow and linked source material. The longer-term test is whether someone can understand a project here without first reading its code.
